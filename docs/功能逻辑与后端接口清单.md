# 猎头匹配 Agent：功能逻辑与后端接口清单

版本：基于 main 当前代码（2026-08）。

产品一句话：顾问上传候选人简历，选择客户重点项目，系统按「简历 x 项目」逐一匹配，生成内部匹配报告；通过人工审核后再生成客户推荐报告。

## 一、当前功能逻辑

### 1. 发起匹配

页面地址：`/match`

流程：
1. 上传简历：PDF/DOCX/TXT，一份文件等于一位候选人，最多 10 份。
2. 选择项目：只展示项目管理中标记为重点项目的岗位，最多 10 个。
3. 发起匹配：后端执行 `简历 x 项目`，最多 100 个组合。
4. 状态刷新：前端只在页面进入、窗口 focus、用户触发数据变更事件时查询状态，不做固定定时轮询。
5. 完成后进入 `/match/runs`，展示综述和全部匹配报告卡片。

### 2. 匹配打分

后端先把 JD、公司提示词、岗位提示词和岗位能力标签词典组装成匹配输入，并拆成结构化条件：
- 硬性条件：学历、年限、城市、薪资、核心技能、必须行业经验、一票否决项等。
- 核心能力/岗位主线：岗位族、岗位主线一致性、关键职责经验、不可替代技能。
- 优先条件：大厂背景、同类项目、0-1、管理规模、AI Agent、出海、商业化、稳定性等。

模型只负责逐条判断：
- 满足 = 1
- 不满足 = 0
- 待确认 = 0，且计入分母

系统负责算分：
- 按条件类型和岗位主线计算分维度得分。
- 对硬性 blocker、核心能力缺失、岗位主线不一致等情况执行封顶或降档。
- 对年龄推断、跳槽频率、谈薪等不确定信息按风险/偏好处理，不直接当作一票否决。
- 最终输出综合参考得分、推荐等级、条件明细和风险建议。

结论口径：
- 硬性条件有不满足：请重点关注，慎重推荐。
- 硬性条件全部满足但有待确认：可进入人工审核，需补充确认。
- 综合参考得分 >= 80 分：进入人工审核。
- 综合参考得分 >= 90 分：建议推荐客户。
- “初筛通过”只代表客户认可，属于人工审核后的客户反馈，不由模型预估。

### 3. 三层提示词

生效顺序：通用提示词 + 公司提示词 + 岗位提示词。

位置：
- 通用提示词：`提示词管理 / 通用提示词`
- 公司提示词：`提示词管理 / 公司提示词`，也可在客户详情页维护
- 岗位提示词：`提示词管理 / 岗位提示词`，也可由岗位详情里的硬性要求/优先条件自动生成

规则：
- 新建提示词即生成新版本，并默认成为 active。
- 匹配时只传当前 active 版本。
- 历史版本只存在库里，不进入本次 LLM prompt。
- 每份报告保存当次 `prompt_snapshot_json`，后续提示词更新不影响旧报告回放。

### 4. Few-shot 规则

当前明细阶段默认带 3 个极短 few-shot 示例，用来稳定 rows 的拆解粒度、`condition_type`、`label` 和 `note` 写法。

示例覆盖：
- 技术岗：AI Agent 工程师。
- 产品/运营岗：增长运营。
- 销售/交付类：高净值房产管家。

使用边界：
- few-shot 只学习格式和判断口径，不提供业务事实。
- 实际条件必须来自本次 JD、公司提示词、岗位提示词和候选人简历。
- 不允许照搬示例里的条件。
- 示例数量固定为 3 个短例，避免 token 过高；正式版可做后台配置开关。

### 5. 客户、项目、岗位

- 客户管理：独立 `/api/companies` 数据源，分开维护唯一的营业执照名称与公司简称；历史公司名迁移为简称，营业执照名称由顾问核对后补录。
- 项目管理：重点岗位集合，UI 与岗位管理分开；数据上复用 `positions.is_project`。
- 岗位管理：全量岗位池，维护完整 JD、岗位字段、岗位提示词；支持手动新增/编辑和本地 PDF/DOCX/XLSX/TXT 文件导入，岗位 Excel 优先按表头结构化拆分，其他文件导入解析走统一 LLM 配置。
- 客户管理：维护客户公司信息；支持手动新增/编辑和本地 PDF/DOCX/XLSX/TXT 文件导入，导入解析走统一 LLM 配置。

### 6. 进程管理

页面地址：`/process`

用途：记录进入人工审核后的真实推进状态和客户反馈。

当前字段：
- 姓名
- 推荐岗位
- 客户
- 当前阶段
- 客户反馈
- 拒绝原因
- 顾问

客户反馈用于后续统计，不反向改写历史 AI 匹配分。

## 二、减少接口调用的现行方案

已做或应保持的拆分：
- `/api/projects`：发起匹配页专用，只返回重点项目卡片字段。
- `/api/positions/options`：提示词页/进程页下拉专用，只返回 `id/title/company/seq_no`。
- `/api/companies`：客户页专用，不再从岗位表前端聚合客户。
- `/api/tracking`：直接返回 `position_title/company`，进程页不再全量拉岗位表做前端匹配。
- `/api/tracking/init`：合并进程页初始化所需的 meta、users、position options。

页面调用原则：
- 编辑详情页可以拉完整对象。
- 列表页优先拉轻量列表。
- 下拉选项用 options 接口。
- 不为展示一个名称去全量拉另一张表。

## 三、节省 LLM token 的现行方案

匹配时不再默认传完整简历全文和完整 JD：

1. 简历侧：
   - 优先传 `resume_struct_json` 生成的结构化摘要。
   - 只传基本信息、教育、工作经历摘要、项目经历摘要、技能关键词。
   - 根据岗位要求关键词抽取相关简历原文片段。
   - 临时上传简历的 `resume_text/resume_struct_json` 只在保留期内保存，用于报告生成和短期核验；过期后由后台清理或管理员手动清理入口清空，不删除历史匹配报告。

2. JD 侧：
   - 优先传 `jd_struct_json` 中的结构化字段和 `requirements`。
   - JD 原文只作为补充片段截取，不默认整段塞入。

3. 提示词侧：
   - 只传通用/公司/岗位三层 active 版本。
   - 历史版本不进入 LLM 请求。

4. 复用侧：
   - 对同一候选人内容、同一岗位版本、同一三层提示词版本，如果输入签名未变化，后端复用已有匹配结果，不重复请求 LLM。
   - 复用时新报告会记录 `reused_from_result_id`，并保留 `input_signature` 便于追溯。

## 六、客户推荐报告现行实现

客户推荐报告已由后端生成并落库，存储在 `client_recommendation_reports` 表中，支持 AI 初稿、人工编辑、版本递增、飞书同步和导出。

生成规则：
- 默认仅允许综合参考得分 >= 90 或人工审核通过的报告生成。
- 客户版只展示客户需要的信息：推荐人选、推荐岗位、性别、年龄、学历、期望地点、目前状态、目前薪酬、期望薪酬、用工形式、推荐理由、补充说明、原简历附件。
- 不展示内部字段：硬性/优先得分、prompt、token、模型日志、人工审核过程、内部拒绝原因。
- 推荐理由可以由 LLM 生成，但必须基于简历和匹配报告证据，不允许编造。
- 每次生成保存模型名、提示词版本、token、原始输出，便于追溯。

## 七、后续必须确认

1. 是否需要按客户、顾问或租户进一步隔离数据可见范围，并配套审计日志。
2. 简历附件下载必须鉴权、限时、记日志。
3. 顾问默认只能看自己负责的数据，管理员可看全部。
4. 图片简历、扫描 PDF、旧版 `.doc` 是否接 OCR/转换服务。
5. 报告页当前按前端 HTML 导出 Word/PDF，后端导出接口保留给 API/批处理；后续如要统一版式，需要确定唯一导出通道。
6. 批量匹配是否改为 batch_id 主键管理。
7. 客户反馈是否允许反哺提示词，是否需要人工审批后才生效。
